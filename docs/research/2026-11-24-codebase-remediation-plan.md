## First changes and their acceptance tests

Each numbered entry is a reviewable change or an explicitly ordered sequence. Functional owners are given by the linked modules. Start independent entries together. Use the failure cases as test inputs on clean fixtures. For security boundaries, inspect the decision, captured arguments or persisted data using inert markers.

1. **Validate Session Chat revisions (A042-01).** Both whole-commit and file-specific reads accept a revision from a timeline row. Accept the supported hex object-ID forms, resolve a unique local commit with option parsing terminated, then pass only its canonical ID to the display command. The remote-entry fixture uses a seven-character abbreviation. **Merge dependencies.** The registry, Git and policy fixes can ship independently. Four orderings matter for persistence and rollout.

| Before | Then | Failure this ordering prevents |
| --- | --- | --- |
| Strict per-file load and write guards (change 8) | Enable the new outgoing save path on the same files (change 9) | Switching projects could otherwise flush a fallback board over a recoverable one. |
| Capture boundary and protection for old queued rows (change 3) | Correct already-synced rows with a new hash and verify ingest | The first upgraded connection could upload old content, or acknowledge a correction without applying it. |

| Per-document write acknowledgement and the native quit decision | Enable close/restart with a dirty document or staged app | A successful exit could outrun the last save. |

## Verification, release and closure

1. **At intake**, record the ID, current `dev` SHA, owning module, reported confidence, expected user-visible outcome and smallest fixture or native observation. For a `LIKELY` race use a controllable delay, barrier or failure injection. For platform behavior record OS, architecture, webview and package. A passing counterexample can close a hypothesis with evidence. An unavailable native runner leaves it open. Preserve the original report and track implementation status separately.
2. **During a fix**, exercise the normal entry point and check the durable state at the other end. For frontend changes use `bun run lint`, `bun run format:check`, `bun run typecheck` and the affected `bun run test <paths>` suites. Use `bun run dev` for interaction and `bun run dev:app` for invoke/event paths. For Rust run `cargo test --locked -p <crate>` or the relevant app library filter. In particular run `atlas-engine-apply-patch` and `atlas-engine-shell-command` explicitly for their changes. Test `atlas-kb-server` from its own directory for export changes. [Contribution gates](../../CONTRIBUTING.md) · [Workspace boundaries](../../Cargo.toml)
3. **Before a PR to `dev`**, run `bun run ci:local --base origin/dev` and check the planned jobs against `node scripts/ci-affected.mjs --base origin/dev`. Exercise Linux sandbox behavior on Linux and actual native UI/package behavior on the matching OS. Add a regression to the owning suite for each distinct defect. For altered IPC/event fields run contract suites and update mocks. For session-delta additions update Rust consumers and the contract and regenerate with `bun run bindings:gen`. Read each affected contract’s docblock first. [CI workflow](../../.github/workflows/ci.yml) · [Wire contract](../../crates/atlas-agent-wire/tests/contract.rs) · [Linux release verification](../../.github/workflows/release-linux.yml)
4. **Before promoting a fix release**, rehearse upgrade from the currently shipped data shapes, including a damaged file, a pending capture upload and a pending local edit. Interrupt the migration or staging operation, restart and retry. Preserve original bytes/rows until a verified successor is durable. An unsuccessful scrub holds the affected upload, a failed save retains the draft, and a failed update keeps the previous verified app bootable. Ship independent protections as they pass. Track historical cloud cleanup and missing platform runs as separate open work. Handle vulnerability reports through the repository’s private channel. [Release model](../adr/0030-dev-is-the-integration-branch-main-takes-promotions.md) · [Security reporting](../../.github/SECURITY.md)
5. **To close an ID**, link its PR/commit, the failing-before/passing-after check or documented counterexample, platform result where relevant and first release carrying the fix. Track `open`, `investigating`, `fixed on dev`, `verified in release` or `disproved with evidence` for each ID. Track a shared cause once while preserving all of its acceptance cases. Keep the ledger’s excluded surfaces distinct from defects actually found.
